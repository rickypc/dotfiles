# Universal recovery and change handling

## Resume safely

Resume from the central intent, not an inferred directory tree. Load its
gray-matter through the lifecycle runtime, inspect the stage ledger and
audit events, confirm the selected project root and CBM index, then request the
packet for the active stage. Read the evidence sections relevant to that stage
before doing new work. A completed or skipped record is evidence of what
happened; do not replay it merely because the conversation restarted.

If intent frontmatter is invalid, stop normal progression and report that it
is malformed. The error must explain that AIDLC commands cannot safely run
until the intent is repaired through the gray-matter lifecycle boundary. Do
not attempt to reconstruct a route from filename guesses, a common home path,
or an upstream active-space tree.

## Missing context

First distinguish an intentionally skipped conditional stage from a missing
result. A skipped stage produces no artifact and is not a defect. For a needed
fact, use the stage's documented fallback: project instructions, verified
codebase-memory research, validated knowledge-base context, or a focused user
question. Never invent the content of a missing design or requirements record.

## New evidence and changes

New references supplied mid-stage are evidence for the current stage, not an
implicit instruction to advance. Record what they change, rerun the relevant
sensor, and continue through the selected route. When evidence changes an
earlier decision, identify the affected requirements, design, implementation,
and validation evidence; use `replan` to preserve that causality before
revisiting the smallest affected boundary.

For a material scope or architecture change, return to the stage that owns the
decision—normally 1.4, 2.3, or 2.6—then update downstream plan and code
evidence. Preserve unaffected work and do not hand-edit the route. For a
contradiction, quote the conflicting sources, say what decision it blocks, and
ask the user rather than arbitrarily favoring one.

## Failure severity

Critical: malformed intent state, missing authorization, an unsafe ambiguous
change, or a final-gate failure that cannot be repaired. Stop and expose exact
evidence. High: contradicting requirements, missing dependency facts, or an
invalid design conclusion; resolve before advancing. Medium: incomplete
context or unclear preference; research first, then ask only if material. Low:
formatting or naming issues that do not alter behavior; correct them while
preserving evidence. No severity permits a false completion or gate waiver.
